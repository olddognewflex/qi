# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make test                       # go test ./...
make tidy                       # go mod tidy
make run                        # go run ./cmd/qi
go test ./internal/vault -run TestParseTaskLine   # single test
go build -o bin/qi ./cmd/qi     # build CLI (no `make build` target)
go build -o bin/qid ./cmd/qid   # build daemon
go build -o bin/qi-mcp ./cmd/qi-mcp   # build MCP server
```

Go 1.25+. Module path is `qi`; import internal packages as `qi/internal/...`.

`qi` requires `vault_path` resolved from (priority order) env `QI_VAULT_PATH` > `~/.config/qi/config.toml` (`XDG_CONFIG_HOME` honored) > error. `QI_TASK_FILE_PATH` overrides task file. Without a vault path, every command exits at `commands.NewRootCommand` because `config.Load()` runs in the root constructor.

## Architecture

Three binaries:
- `cmd/qi/main.go` — stateless CLI; calls `commands.NewRootCommand().Execute()`. Fast, no AI on the hot path.
- `cmd/qid/main.go` — long-running daemon. Hosts the tool registry and serves a JSON-RPC 2.0 API over a unix-domain socket. Wires builtin tools, deterministic skills, external MCP servers, the policy gate, and the approval queue.
- `cmd/qi-mcp/main.go` — MCP server (stdio subprocess of an AI client). Dials qid, fetches the live tool catalog, and re-publishes it to MCP clients (e.g. Claude Desktop).

### CLI layer (`qi`)

Strict layered Cobra CLI. Direction of dependency is one-way: `cmd → commands → service → {vault, index, calendar} → domain`.

- `internal/commands/` — **thin** Cobra handlers. Wiring only: parse flags, call service, format output. No business logic. New subcommands register in `root.go`. `qi task add` takes `--project` (free-form tag) or `--client` (validated client name → routes to the client `task_file`; mutually exclusive). `qi note new` takes `--client`/`--project` to write into that vault's configured notes dir (`notes_path`, default `00-inbox`; via `Config.NoteVaultFor`) instead of the main vault. `ai.go` is the client side of qid: `qi ai tools list|call`, `qi ai run`, `qi ai approvals|approve|deny`. `launch.go` is `qi launch harness` (alias `qi launch ai`): resolves an external AI harness via `Config.ResolveLaunchTarget` and runs it with `QI_VAULT_PATH` exported (matched vault, else global) and cwd set to the resolved working dir (project `dev_path` / client `dev_root`, else the current dir is inherited — no chdir) — non-detached harnesses replace the qi process (`syscall.Exec`, unix), detached ones spawn and return. Platform exec split lives in `launch_exec_unix.go` / `launch_exec_windows.go`. `doctor.go` is `qi doctor`: a read-only health check that reports per-component status (config file, vault dirs, qid socket, search-index freshness, cloud-queue Worker reachability) and exits non-zero if any check **fails** — `warn` flags optional/lazy components (no daemon, unbuilt index, lazily-created subdirs) and does not fail. Index freshness is a stat-only mtime compare (`index.DBPath()` vs the newest vault `.md`, no content reads); Worker reachability is a 5s `Pull(limit=1)` skipped when `[remote_queue]` is disabled. `remote_status.go` is `qi remote-status`: a read-only `Stats()` call on the cloud queue printing pending + deadletter counts (no-op when `[remote_queue]` disabled); pairs with `remote_drain.go` (`qi remote-drain`). Queued items carry a `kind` (`task`|`note`|`capture`, default `task` — absent kind = task, so tasks-only clients are unchanged) and `qi remote-drain` routes by kind: `task`→`TaskService.CreateTask` (id-idempotent), `note`→`NoteService.AddNote(text, "")`, `capture`→`CaptureService.Capture(text)`. note/capture ignore project/client/dates and are NOT id-deduped (a rare ack-failure re-drain can duplicate them — cheap/reversible, acceptable); an unknown kind deadletters rather than being silently dropped. `inbox.go` is `qi inbox`: a Bubble Tea triage flow over `InboxService.List`, applying one chosen action per capture; `--dry-run` prints proposals without the TUI (and without writing). The interactive path needs a TTY (errors otherwise, like `qi task done`). `search.go` is `qi search <query>`: a read-only unified FTS search across the whole vault (notes/tasks/dailies/inbox), prefixing each hit with a `[kind]` tag; `--kind`/`-k` filters by kind (note|task|daily|inbox|other) and `--limit`/`-n` caps results (default 20). `--semantic`/`-s` switches to opt-in cosine ranking over local embeddings (requires `[embeddings] enabled` + a prior `qi embed`), appending `(0.NN)` scores. `embed.go` is `qi embed`: builds the opt-in semantic index — walks the vault, embeds each note via Ollama (`internal/embed`), and stores the vectors in SQLite (`note_embeddings`); errors out unless `[embeddings] enabled = true`, and warns-and-continues on a per-note embed failure. `plan.go` is `qi plan [date]`: auto-time-blocks open tasks into the daily note's `## Schedule` via `vault.ReplaceSection`, packing each task into the next free slot while preserving hand-authored entries and skipping already-scheduled titles (idempotent). Rendered range lines use an ASCII hyphen (`- HH:MM-HH:MM Title #proj`) so the local calendar provider parses them and they surface in `qi agenda` for free. By default plans tasks due/scheduled that day (`--all` for every open task); flags `--start` (HH:MM, default 09:00), `--block` (duration, default 30m), `--limit` (default 6), `--project`/`-p`, `--dry-run`. All logic lives in `service.PlanBlocks`/`MergeAndRender` + `calendar.ParseScheduleEntries`/`ScheduleEntry.Render`; the handler is thin.
- `internal/service/` — all business logic. `TaskService`, `CaptureService`, `NoteService`, `AgendaService`, `InboxService`. Services are plain structs constructed per-command from `config.Config`. Fuzzy matching, sorting, validation all live here. `InboxService` owns inbox triage — `List` (deterministic task/note/archive heuristics over `00-inbox/`) and `Apply` (task/note/archive/delete + path-traversal guard); both `qi inbox` and the `skill.process-inbox`/`-apply` tools drive the vault through it (the skill is a thin JSON wrapper).
- `internal/domain/` — pure value types (`Task`, `Note`, `Event`). No I/O, no deps.
- `internal/vault/` — markdown read/write. **Obsidian-compatible** task line format must be preserved: `- [ ] text #project 🔁 every week ⏳ YYYY-MM-DD 📅 YYYY-MM-DD ✅ YYYY-MM-DD ^qi-id`. See `ParseTaskLine`/`FormatTaskLine` in `tasks.go`; round-trip tests in `tasks_test.go` are load-bearing. The `✅ YYYY-MM-DD` done-date round-trips into `Task.CompletedAt` (emitted after `📅 due`, stamped by `CompleteTask`). The Obsidian Tasks `🔁 <rule>` recurrence marker is parsed into `Task.Recurrence` and re-emitted in canonical order (after tags, before `⏳`/`📅`); `recurrence.go` (`NextRecurrence`) computes the next occurrence for the supported rule subset (`every [N] day|week|month|year`, optional `when done`). Completing a recurring dated task (`TaskService.CompleteTask`) keeps the original `- [x]` line's marker and appends a fresh open instance with a new id and advanced dates.
- `internal/index/` — SQLite FTS5 index via `modernc.org/sqlite` (pure-Go, no CGO). Lives at `$XDG_DATA_HOME/qi/qi.db` (or `~/.local/share/qi/qi.db`). `Rebuild` walks **all** vault markdown (`vault.WalkVault`), so the single `notes` FTS table physically covers tasks, dailies, inbox, and notes — not just `20-notes/`. `qi search` exposes a unified, kind-labelled search over that table: `SearchWith` classifies each hit by the vault subdir in its path at query time (`classifyKind` → note/task/daily/inbox/other) and optionally filters by kind, so no schema column backs the labels. `qi note search` is scoped to the `note` kind via the same path. The index also **optionally** stores per-note embeddings in a `note_embeddings` table (path/model/dim/vector BLOB/updated_at) for opt-in semantic search: `internal/embed` is a tiny Ollama `/api/embed` client, `qi embed` builds the vectors, and `qi search --semantic` cosine-ranks them in Go (no SQLite vector ext; `embeddings.go` holds `encodeVector`/`decodeVector`/`cosine`/`SemanticSearch`, reusing #7's `classifyKind` labels). The index stores/ranks raw vectors only — it never imports `embed`; the command embeds the query and passes the `[]float32` in. **Derived state** — both FTS and embeddings are fully rebuildable from markdown (`index rebuild` / `qi embed`); opt-in via `[embeddings] enabled`. Never the source of truth.
- `internal/calendar/` — `Provider` interface aggregates events into `AgendaService`. All impls are **read-only**; qi has no calendar write path. Five impls: `LocalProvider` (parses `## Schedule` block in `30-daily/YYYY-MM-DD.md`, format `- HH:MM[-HH:MM] Title [#tag]`), `ICSProvider` (HTTP fetch of `.ics`; note its `toEvent` ignores RRULE — a recurring event surfaces once, at its DTSTART), `CalDAVProvider` (App Password), `GoogleProvider` (OAuth; token + keychain helpers in `google_auth.go`/`google_token.go`/`keychain.go`), `VdirProvider` (`vdir.go`; reads a [vdir](https://vdirsyncer.readthedocs.io/en/stable/vdir.html) collection — a flat dir of one `.ics` per event plus `displayname`/`color`/`order` metadata — so vdirsyncer owns CalDAV/Google transport while qi just reads local files: no network, works offline, interops with khal. Non-recursive; skips non-`.ics` entries, which also covers vdirsyncer's transient `.tmp` writes; tolerates a malformed file but reports skip counts on stderr. `DiscoverVdir` mirrors khal's `type = discover`: one provider per subdir, named by `displayname`, dot-dirs skipped). Add a provider → register it in `commands/agenda.go`.
  - **Recurrence expansion** (`caldav.go`) is shared by `CalDAVProvider` and `VdirProvider`: `expandCalendarEvents` groups a calendar object's VEVENTs by non-empty UID into a base plus its `RECURRENCE-ID` overrides, expands the base's recurrence set, then folds the overrides in — `RANGE=THISANDFUTURE` reshapes a run of slots in place, then single-instance overrides replace or cancel individual slots (so a single override wins inside a THISANDFUTURE run, the precedence RFC 5545 §3.8.4.4 requires). Matching is by **slot identity, never wall-clock start**, so chained overrides can't delete each other; UID-less components each get their own group so they never merge. `domain.Event.ID` is consequently heterogeneous: a bare UID for a non-recurring event, `<uid>-<RFC3339 slot start>` for an occurrence — an opaque key encoding slot identity, not a UID. Known gap: an override carrying its own RRULE has that rule ignored (the base rule's slots are shifted instead) — see `applyThisAndFuture`.
- `internal/tui/` — Bubble Tea pickers for interactive CLI selection.
- `internal/config/` — TOML loader with env var overrides. Derives `InboxPath`, `NotesPath`, `DailyPath` from `VaultPath` (subdirs `00-inbox`, `20-notes`, `30-daily`). `TaskFilePath` defaults to `10-tasks/inbox.md` relative to vault. Also parses `[[mcp_servers]]` (external MCP servers qid connects to), the calendar sections `[[ics_calendars]]` / `[[caldav_calendars]]` / `[[google_calendars]]` + `[google_oauth]` / `[[vdir_calendars]]` (each a `name` plus its transport config; vdir takes a `path` — `~` and relative paths resolve via `expandUserPath` — and an optional `discover = true` meaning the path is a root of collections rather than one collection, entries missing `name`/`path` being skipped as with the other kinds), the `[ai]` section (provider/model defaults for `qi ai run`), `[[client]]` entries with nested `[[client.project]]` (a client = one `vault_path` + `dev_root` shared across its projects; each project has a `#tag`-matching `project` key, optional `path` (a base subdir within the vault under which relative `task_file`/`notes_path` — and their defaults — resolve; absolute values escape it), optional `task_file` (projection task file), optional `notes_path` (note dir for `qi note new --project`, default `00-inbox`, inherits the client's `notes_path` when unset), and optional `dev_path` (absolute or relative to `dev_root`) used as the `qi launch harness` working dir; the client itself takes an optional `notes_path` (default `00-inbox`) for `qi note new --client`). Clients flatten into `Config.Projects` at load (each project inheriting the client `vault_path`/`launch`, paths resolved absolute) so `sync`/`launch` consume the flat list; `Config.Clients` is retained for client-name launch resolution. A `[[client]]` with `task_file` also flattens into a **synthetic** project tagged by the client name (for `sync` routing of client-wide tasks); synthetic projects are excluded from `ProjectByName` so they never shadow client-name launch resolution. `Config.NoteVaultFor(client, project)` resolves which vault a `qi note new` lands in, and the `[launch]` section (default AI harness for `qi launch harness`, with optional per-`[[project]]` `[project.launch]` overrides). `Config.ResolveLaunchTarget(flag)` resolves the launch target (`--project` flag, else `$WORK_CONTEXT`) **project-first, then client**: a project match runs `[client.project.launch]` > `[client.launch]` > `[launch]` > `$AI_HARNESS` > `$AI_EDITOR` with cwd = project `dev_path`; a client match runs `[client.launch]` > `[launch]` > env with cwd = client `dev_root`; no match runs the global harness in the current dir. An explicit flag matching neither errors; an unmatched `$WORK_CONTEXT` is lenient and falls through to the global default. `QI_VAULT_PATH` is exported as the matched vault (else global).

### Daemon layer (`qid` / `qi-mcp`)

qid is the orchestration core. Every tool call — from the CLI, the AI planner, or an MCP client — flows through one registry and one policy gate. The **caller identity** drives the trust decision: `cli` callers and read-only tools run immediately; any non-cli caller mutating state routes through the approval queue.

- `internal/tools/` — in-memory tool registry. Tools come from three sources: `SourceLocal` (compiled-in Go), `SourceMCP` (connected external MCP servers), `SourceSkill` (composed workflows). Derived state — rebuilt from code plus live MCP connections, never persisted. `Execute` dispatches local handlers directly and MCP tools through the manager.
- `internal/tools/builtin/` — compiled-in `SourceLocal` tools: `vault.capture`, `task.add` (mutating), `task.list`, `note.search`, `agenda.today`. Each wraps the matching service and exposes a JSON schema; registered in `cmd/qid/main.go`.
- `internal/skills/` — deterministic composed workflows exposed as `SourceSkill` tools: `daily-review`, `process-inbox` (read-only; proposes task/note/archive per `00-inbox/` capture via deterministic heuristics) + `process-inbox-apply` (mutating; executes one proposed action), and `weekly-review` (read-only; aggregates the week's completed tasks by their ✅ done-date, capture volume from inbox+archive by filename date, and daily `## Logs` highlights into a proposed review note) + `weekly-review-apply` (mutating, gated; writes a given title+body as a note), `quick-task` (mutating, gated; add a task + return the refreshed open list in one call — composition over the bare `task.add` builtin), and `session-log` (mutating, gated; append a timestamped entry to today's daily `## Logs`, the headless equivalent of `qi daily cp`). Chain existing services and read the vault; **never call an LLM, never write silently.** Read-only by default; mutating skills must set `Mutating: true` so policy gates them.
- `internal/daemon/` — JSON-RPC 2.0 server. Newline-delimited JSON over a unix-domain socket (`server.go`, `wire.go`, `socket.go`). `internal/daemon/client/` is the Go client used by `qi ai` and `qi-mcp`; it carries the caller identity and detects approval-pending results via `IsPending`.
- `internal/policy/` — decides allow / queue / refuse for each call. Deterministic and conservative: anything a non-cli caller wants to mutate routes through the approval queue. `DefaultDecider` is the wired default.
- `internal/approval/` — in-memory queue of mutating calls policy did not auto-allow, plus an **append-only JSONL audit log** (the durable record). Every state transition (queued → approved/denied → executed/failed) is logged.
- `internal/mcp/` — connects qid to external MCP servers listed in `config.MCPServers`, surfaces their tools under namespace `mcp.<serverID>.<toolName>`, and routes `Execute` calls back to the right client.
- `internal/qimcp/` — the inverse bridge: re-publishes qid's tools to AI clients via MCP, forwarding each call back through the daemon client as `caller="mcp:<sessionID>"` so mutations hit the approval queue. Drives `cmd/qi-mcp`.
- `internal/ai/` — LLM tool-use loop (`Planner`) against qid's catalog. Providers: Anthropic and Ollama. Executes proposed tool calls as `caller="ai-planner:<sessionID>"`; mutating calls surface as approval-pending results — the planner never bypasses qid's policy gate.
- `internal/watcher/` — opt-in fsnotify-driven auto-reconcile. When `[sync] watch = true`, qid watches the canon + projection task dirs (`watcher.DirsFor(cfg)`) and runs the existing `sync.Reconcile` (debounced via `debounce_ms`, default 750) on any `.md` change, eliminating manual `qi sync`. The watcher depends only on fsnotify/config/stdlib; the reconcile is injected as a closure (`cmd/qid` wires index + sync). Off by default — no watcher starts unless `watch` is set.
- `internal/notify/` — opt-in morning due-today notifier. When `[notify] due_today = true`, qid schedules one macOS notification each day at `[notify] at` (HH:MM 24h, default 08:00 via `notify.DefaultAt`) listing tasks due/scheduled today. Read-only, no policy gate, off by default. The package imports only stdlib: a `DailyScheduler` (pure `nextFire`/`parseHHMM` math) takes a plain `func()` callback, and a `Notifier` (`osascript` banner on darwin via a safely-escaped AppleScript, `*slog.Logger` fallback elsewhere) takes plain strings. `cmd/qid` wires them via `makeDueTodayNotifier` (lists open tasks → `service.FilterDueToday` → one summary notification; quiet when nothing is due). The due-today filtering lives in `service` (`FilterDueToday`); notify never imports service/domain.

### Non-negotiable invariants

1. **Markdown is canonical.** Vault files must remain readable/usable without `qi`. SQLite is a derived index; never store anything there that isn't in the markdown.
2. **`qi capture` hot path <100ms.** No network, no AI, no blocking. `vault.WriteCapture` writes a timestamped `.md` to `00-inbox/` and returns.
3. **AI is opt-in and confirmation-gated.** No silent LLM calls. Any AI-proposed mutation requires explicit user approval before writing to the vault. This is enforced structurally in qid: non-cli callers (`ai-planner:*`, `mcp:*`) can never mutate directly — `internal/policy` routes their mutations into `internal/approval`, where a human runs `qi ai approve <id>` (or `deny`). Don't add a code path that lets a non-cli caller bypass that gate.
4. **Obsidian task-line compatibility.** Don't change `ParseTaskLine`/`FormatTaskLine` output format without verifying round-trip with existing vault files. Project tag becomes the first `#tag`; due date is `📅 YYYY-MM-DD`; recurrence is `🔁 <rule>` (emitted after tags, before `⏳`/`📅`); the done-date is `✅ YYYY-MM-DD` (after `📅 due`). A foreign `^ref` or unsupported recurrence rule must survive untouched.

### Vault layout (writes target these paths)

```
vault/
├── 00-inbox/        # capture writes here (timestamped files)
├── 10-tasks/inbox.md
├── 20-notes/
└── 30-daily/YYYY-MM-DD.md   # local calendar source
```

Machine-local (never synced, not in vault):
- `$XDG_DATA_HOME/qi/qi.db` (or `~/.local/share/qi/qi.db`) — SQLite note index.
- `$XDG_RUNTIME_DIR/qi/qid.sock` → `$XDG_STATE_HOME/qi/qid.sock` → `~/.local/state/qi/qid.sock` — qid unix socket (first that resolves; 0600). `--socket` overrides on both qid and the clients.
- `audit.log` next to the socket — append-only JSONL approval audit log.

## Git hooks

Plugin-style hooks: enabled plugins listed in `git config --get-all hooks.enabled-plugins`, plugin code lives under `.git/hooks/<plugin>/`. Check the config before assuming hooks are inactive — they will run on commit/push.

## Scope boundaries (from AGENTS.md)

`qi` exposes local tools and runs deterministic skills. It does **not** autonomously chain tools, silently mutate vault state, hide tool execution, or invent workflows. When adding features, keep them deterministic and explicit; route any AI-driven action through a confirm-before-write flow.
